# Architecture review and refactoring plan

**Recommendation:** Keep the existing projects. Start with logging and counter correctness, then separate moderation decisions from their side effects. Moving classes between projects first would make the diff larger without addressing the main risks.

**Scope:** Static review of the attached spam detector and the repository paths for webhook processing, OpenAI calls, message counting, human review, and the React moderation workflow. Search indexing and existing tests were inspected for useful patterns. This is not an infrastructure or deployment audit. No production behavior was changed or tests run for this report.

## Implementation plan

Each step is independently reviewable. Steps 3 and 4 need not wait for one another after step 2.

1. **Make diagnostics safe.** Replace raw URLs, payloads and model responses with operation, status and finish reason. Emit one sanitized failure event rather than serializing the exception indiscriminately. Verify with a capturing logger and synthetic URL/token and message markers on success and failure. If debug logging was enabled in deployment, check retention and rotate the token if exposure is confirmed.
2. **Give the counter one owner.** For ordinary eligible senders, introduce a repository operation that increments and returns the *prior* count; use conditional creation/ETag updates and bounded conflict retries. Await it before branching. Reports remain read-only. Test simultaneous increments from an absent and an existing row, the 99/100 eligibility boundary, both cache hits, and a failed write. Keep webhook redelivery deduplication separate: atomic increments alone do not count unique updates.
3. **Make the automated decision path readable.** First characterize reported vs ordinary messages, clean/spam cache hits, model scores 94/95, and model failure. Then extract named eligibility and verdict rules, a deterministic hash builder, and a shared enforcement routine. Keep the existing hash input fields, serialization, encoding and output unchanged; pin a representative hash before extraction. Keep the processor as the visible coordinator. Follow [PostIndexer](../src/bot/TelegramAntiSpamBot.Search/Indexing/PostIndexer.cs): short orchestration with named operations, not a new framework.
4. **Narrow the OpenAI adapter.** Share the usable-completion/text operation, keep the two response parsers and failure policies explicit, and classify a filter rejection only when provider evidence identifies it. Retain fresh options and response formats per call. Run the existing malformed-response, fallback and concurrency cases in [ImageAnalysisTests](../tests/TelegramAntiSpamBot.IntegrationTests/ImageAnalysisTests.cs); add coverage distinguishing an ordinary bad request from a filter rejection.
5. **Define retry semantics for human review before changing the UI.** Extract the review workflow from HTTP parsing. Agree on an operator-visible outcome for uncertain Telegram sends; use a conditional claim to prevent simultaneous processing, and persist progress for acknowledged chunks. Do not promise exactly-once Telegram delivery: a send may succeed before progress can be saved. Test competing decisions, partial sends and deletion failure; retain the UI warning until the API can distinguish completed, pending and uncertain outcomes. Verify the existing [review API tests](../tests/TelegramAntiSpamBot.IntegrationTests/ReviewFunctionsTests.cs) and [browser review flows](../tests/TelegramAntiSpamBot.WebTests/review.spec.ts).

**Guardrails:** Preserve webhook and review routes, stored hashes, report handling, and Telegram reply/chunk behavior unless a step explicitly changes them. Keep the existing repository interfaces and web hooks where they already isolate a concern. No solution-wide renaming, new shared base class, or project split is needed for these changes.
